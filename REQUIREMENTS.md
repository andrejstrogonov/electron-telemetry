# Требования к приложению Telemetry Viewer

## Функциональные требования

1. Клиент должен загружать данные телеметрии в формате JSON от сервера `/status`.
2. JSON-документ должен включать следующие разделы:
   - `timestamp_ms` — метка времени в миллисекундах.
   - `temperatures_c` — объект температур с именами компонентов и значениями в °C.
   - `power` — объект состояния питания с `voltage_v` и `status`.
   - `fan` — объект управления вентиляторами с `pwm_percent`, `pin_fan_pwm`, `pin_exp`, `exp_flag`.
   - `crc` — объект статуса CRC с `last_block_crc32` и `ok`.
   - `events` — массив событий с `type`, `timestamp_ms`, `value`, `deviation_percent`.
   - `thresholds_c` — объект порогов с `target` и `max_safe`.
   - `system` — объект состояния с `mode` и `uptime_s`.
3. Информация должна отображаться в пользовательском интерфейсе:
   - таблица температур с именем компонента, значением и статусом.
   - состояние питания и напряжение.
   - параметры вентилятора и флаги расширения.
   - статус CRC.
   - список событий.
   - режим системы и время работы (`uptime`).
4. Температуры, превышающие `thresholds_c.max_safe`, должны подсвечиваться как аварийные.
5. Должен быть тестовый режим, использующий локальный файл `data/test-telemetry.json`.
6. Должен быть production режим, использующий внешний URL, заданный переменной окружения `TELEMETRY_SERVER_URL`, или значение по умолчанию `http://localhost:8080/status`.
7. Данные должны валидироваться перед отображением. При неверной структуре приложение должно показывать понятную ошибку и не зависать.

## Нефункциональные требования

1. Безопасность:
   - renderer должен работать с `contextIsolation: true`.
   - `nodeIntegration` должен быть отключен в окне браузера.
2. Надежность:
   - приложение не должно падать при некорректном JSON.
   - ошибки загрузки должны отображаться пользователю.
3. Производительность:
   - отображение данных из локального тестового набора должно быть быстрым (< 200 ms).
   - загрузка данных из production-эндпоинта должна завершаться корректно или давать понятную ошибку.
4. Тестируемость:
   - должна быть возможность запускать `npm run test` для проверки структуры JSON.
   - должна быть возможность запускать `npm run start:test` для работы с тестовыми данными.
   - должна быть возможность запускать `npm run start:prod` для подключения к живому серверу.
5. Поддерживаемость:
   - логика получения данных должна быть отделена от логики рендеринга.
   - структура JSON должна документироваться и легко расширяться.
6. Портируемость:
   - приложение должно работать на Windows, macOS и Linux.

## Запуск и тестирование

### Установка

- `npm install`

### Локальный тестовый режим

- `npm run test` — проверка структуры файла `data/test-telemetry.json`.
- `npm run start:test` — запуск Electron с локальными тестовыми данными.
- `npm run start:test-server` — запустить локальный HTTP-сервер на `http://localhost:8080/status`.

### Production режим

- `npm run start:prod` — запуск Electron для подключения к production-серверу.
- По умолчанию приложение будет запрашивать `http://localhost:8080/status`.
- Если нужен другой сервер, задайте переменную окружения:
  - `cross-env TELEMETRY_SERVER_URL=http://<server>/status npm run start:prod`

### Swagger UI

- `npm run start:swagger` — запустить Swagger UI на `http://localhost:3000`.
- `swagger.html` отображает документацию API на основе `openapi.yaml`.
- В Swagger можно выбрать сервер `http://localhost:8080` для тестовых данных или production сервер для реального `/status`.

### Проверка endpoint

- `npm run test:prod-endpoint` — проверить endpoint `http://localhost:8080/status`, запуская локальный тестовый сервер, если `TELEMETRY_SERVER_URL` не задан.
- Swagger/OpenAPI спецификация доступна в `openapi.yaml` с серверами для теста и продакшена.
